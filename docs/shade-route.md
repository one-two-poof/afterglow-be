# 강남구 그늘길 라우팅 프로토타입

## 목표
강남구 보행 경로를 "그늘이 많은 길" 기준으로 탐색하는 프로토타입.
비용 최소화가 최우선 원칙. DB 없이 인메모리로 동작한다.

## 핵심 설계 (변경하지 말 것)
- 그늘 정보는 **오프라인에서 사전 계산**한다. 서버는 런타임에 기하 연산을 하지 않는다.
- 시간은 30분 버킷. 05:00~20:00 = 31개 버킷.
- 그늘 비율은 uint8 (0~255)로 저장. 최종 산출물은 `shade_table` (버킷 × 엣지).
- 서버는 Spring Boot 단일 인스턴스, 부팅 시 전체를 힙에 로드. DB 없음.
- 지도 위 그림자 폴리곤은 **브라우저에서** 계산한다. 서버는 건물 footprint+높이만 준다.

## 데이터 (실제 확인된 스키마)
### data/raw/AL_D010_11_20260719.shp
- CRS: EPSG:5186 (중부원점, 미터 단위)
- 컬럼: 원본 컬럼명이 A0~A28로 익명화돼 있음(dbf 인코딩 cp949). 매핑 확정:
  BLD_ID=A0, ADDR=A4, USE_NAME=A9, HEIGHT_RAW=A16, SIG_CD=A23, GRND_FLR=A26
- HEIGHT_RAW 필드는 0 또는 비정상값이 섞여 있음 → 2~300m 범위 밖이면 GRND_FLR * 3.3 으로 폴백
- 강남구 필터: SIG_CD == '11680'

### data/raw/street_trees.csv
- 미구현: 두 진행 리포트(2026-08-06, 2026-08-12) 모두 "가로수 그늘 미반영, 건물 그림자만 계산" 상태로 보고됨 — 컬럼 확인 자체가 이뤄진 적 없음
- 수관 반경은 데이터에 없음 → 일괄 2.5m 버퍼, 높이 7m로 가정

## 좌표계 규칙 (버그 1순위)
- **모든 기하 연산은 EPSG:5186에서 한다.** 그림자 이동 거리는 미터 단위.
- 파일로 내보낼 때만 EPSG:4326으로 변환한다.
- WGS84 상태에서 buffer(), translate() 를 호출하는 코드는 무조건 버그다.

## 검증 규칙 (필수)
모든 지리 연산 단계는 `batch/debug/` 에 확인용 산출물을 남긴다.
- 그림자 계산 → matplotlib으로 PNG 저장 (건물 회색, 그림자 반투명)
- 정오와 17:00 두 시각을 나란히 그려서 그림자 방향이 반대인지 보이게 할 것
- 숫자만 출력하고 끝내지 말 것

- 서버: Java 21, Spring Boot 3.x, Gradle, JTS(jts-core, KD-tree 최근접 노드 탐색). **PostGIS/JPA 쓰지 말 것**
- 프론트: MapLibre GL JS, suncalc, turf, pmtiles. 빌드 도구 없이 단일 HTML

## 결정 로그

이 문서의 "핵심 설계"와 "하지 말 것"은 고정 규칙이다.
규칙을 바꾸거나 새로 만든 결정은 여기에 기록한다.

### 범위: 강남구 → 서울 전체

- 원래 규칙: "하지 말 것 — 강남구 밖으로 범위 확장"
- 변경 후: 서울 25개 구 전체. 엣지 26,010 → 1,145,124, 노드 501,728
  (범위 확장 약 15배 × simplify_graph 생략 약 2배가 겹친 수치)
- 이유: 사용자는 서울 전역을 이동하는데 강남구 안에서만 경로가 나오면 기능이
  성립하지 않는다고 판단. 프로토타입 검증이 끝난 시점에 범위 제약을 유지할 이유가 없었음
- 감수한 것: 배치 272.4초 → 63.9분, 힙 542MB(원본 파일 대비 1.31배), 부팅 27.9초.
  이 비용은 확장을 결정한 뒤 파일럿으로 측정했고, 결정 시점에는 추정치가 없었음
- 되돌릴 조건: 배포 인스턴스 메모리가 힙 요구를 못 받칠 경우 구 단위 분할 로딩 검토

### simplify_graph 생략

- 원래 규칙: 그래프 단순화 후 엣지 생성 (강남구 프로토타입은 osmnx 기본값 simplify=True)
- 변경 후: 생략. 교차로가 아닌 중간 노드가 남아 엣지가 약 2배로 유지됨
- 이유: ox.simplify_graph()로 pyrosm 결과를 osmnx 기준에 맞출 수 있음을 강남구에서
  먼저 확인(26,362 vs 26,010). 다만 서울 전체 규모에서는 simplify_graph 단계 자체가
  메모리 초과의 원인 중 하나여서 생략을 선택
- 감수한 것: 엣지·포인트·shade_table이 그만큼 잘게 쪼개져 커짐. 기하는 보존되므로
  그늘 계산 결과의 정확성에는 영향 없음 — 엣지 단위가 짧아질 뿐
- 되돌릴 조건: 구 단위 분할 simplify 등으로 메모리 부담을 피할 수 있게 되면 재적용,
  엣지 수 감소분 측정

### 시간 해상도: 15분 61버킷 → 30분 31버킷

- 원래 규칙: "핵심 설계 — 시간은 15분 버킷. 05:00~20:00 = 61개 버킷"
- 변경 후: 30분 버킷 31개. shade_table 크기·배치 계산량 각각 절반
- 이유: 서울 전체 확장으로 엣지가 크게 늘면서 배치 시간과 테이블 크기를 함께
  줄여야 했음. 사후에 대표일 4개(춘분·하지·추분·동지)의 인접 버킷 간 |diff|를 측정해
  판단을 검증했고, 낮 시간대는 평균 10~20/255로 30분 해상도가 충분함을 확인
- 감수한 것: 조회 시각과 버킷 사이 최대 오차 ±7.5분 → ±15분
  (bucketIndexFor가 반올림으로 가장 가까운 버킷을 선택)
- 되돌릴 조건: 낮 시간대 인접 버킷 |diff|가 유의하게 커지는 데이터 변경이 생기면 재검토
- 비고: 이 측정에서 일출·일몰 구간의 |diff| 급등(159~192/255, 낮 시간대의 약 10배)을
  발견했으나 원인은 해상도가 아니라 그림자 모델의 고도 컷오프였음 → 아래 항목 참조

### 노드 스냅 거리 제한 (규칙 추가)

- 원래 규칙: 없음 — 거리 제한 없이 최근접 노드로 스냅
- 변경 후: MAX_SNAP_DISTANCE_M 300m. 초과 시 NodeSnapTooFarException → 422
- 이유: 그래프 범위 밖 좌표가 먼 노드에 스냅되어, 잘못된 경로가 정상 응답
  (0m / 그늘 0%)으로 반환되고 있었음. RouteController에 요청 로깅이 없어 로그에도
  남지 않았으므로, 임계값 도입과 함께 요청 단위 로깅을 추가
- 감수한 것: 경계부 좌표에서 정상 요청이 거부될 수 있음. 300m라는 임계값 자체는 미검증
- 되돌릴 조건: 정상 요청의 오탐이 관측되면 임계값 재산정

### 저고도 시간대 그늘 라우팅 제공 중단 (규칙 추가) — 미구현

- 원래 규칙: 없음 — 05:00~20:00 전 구간에 그늘 데이터를 제공
- 변경 후(예정): 태양 고도가 기준값 미만인 시간대는 그늘 기준 라우팅을 제공하지 않고
  명시적으로 응답. 최단경로만 반환하거나 해당 취지의 에러를 반환
- 이유: shadow.py의 MIN_ELEVATION_DEG = 3.0에서 그늘 비율을 0으로 끊는데,
  length = height / tan(elevation)이므로 컷오프 직전(3.1도)에서는 tan≈0.054로
  30m 건물이 553m 그림자를 던진다. 결과적으로 "비현실적으로 긴 그림자"와
  "그림자 없음"이 한 버킷 사이에서 계단식으로 점프한다.
  추분 기준 06:44 요청은 06:30 버킷(그늘 없음), 06:46 요청은 07:00 버킷(그늘 폭증)을
  받아 2분 차이로 다른 경로가 나온다. 실제 그림자는 그 사이 거의 변하지 않는다.
  해상도를 15분으로 되돌려도 계단은 남으므로 버킷 문제가 아니다.
  해가 거의 진 시간대에 그늘 기준 경로는 애초에 의미가 없으므로,
  값을 만들어내지 않고 제공 범위를 자르는 쪽을 택한다.
  (스냅 거리 제한과 동일한 원칙 — 조용히 틀린 값을 주느니 명시적으로 알린다)
- 감수한 것: 여름 이른 아침·늦은 저녁 요청에서 그늘 경로를 받을 수 없음
- 후속 과제: 저고도에서 그늘 비율을 부드럽게 감쇠시키면(대기 통과 거리 증가로
  직사광이 약해지는 것을 반영) 불연속 자체가 사라진다. 물리적으로 더 타당한 해법이나
  구현·검증 비용이 있어 범위 차단을 먼저 적용한다
